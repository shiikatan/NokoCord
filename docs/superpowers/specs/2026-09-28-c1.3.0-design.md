# NokoCord Chiaki C1.3.0 Design

Status: scope approved by the maintainer; design checkpoint pending review.

This release is a reliability, compatibility and trust release. It makes the
existing persistent Discord workspace safer to operate before adding more
powerful page modifications.

## Release objective

C1.3.0 should leave users with a clear answer to four questions:

1. Is Discord's current page shape compatible with NokoCord's enhancements?
2. Which Tans are trusted, enabled, healthy and allowed to use native APIs?
3. If a Tan, call, helper or page integration fails, can the user recover
   without losing the Discord session?
4. Is the tested artifact exactly the artifact that was built, tagged and
   published?

The release must preserve the Chiaki contract: one persistent Discord
WKWebView, Discord-owned authentication/messages/media, no raw user-token
transport, no dormant CEF or broker production path, and no silent loss of
session data.

## Scope and non-goals

### In scope

- A feature-level Discord compatibility shield with fail-open behavior.
- A real Safe Mode that injects no Noko scripts or bridge handlers.
- Tan trust records, hash-bound consent, atomic updates, quarantine and one
  rollback snapshot.
- Explicit native capability enforcement for Tans, including removal of
  mutating native access from untrusted page-world packages.
- Tan health and recovery UI shared by Tan Hub and Tans Inspector.
- Targeted DOM observation and cancellation of stale page/presence work.
- Call readiness diagnostics and safer disconnect/reload behavior.
- Apple Music reducer, helper lifecycle and fallback diagnostics.
- Xcode/CLI build parity and reproducible ZIP/checksum packaging.
- Two new capability-free Tans: `noko.focus-shield` and
  `noko.code-workbench`.
- Release documentation, agent guidance, reusable Codex skills and a complete
  release checklist.

### Explicitly out of scope

- A second Discord transport, raw credentials, cookies or user tokens.
- CEF, a broker-backed production client, self-bot behavior or automated
  account actions.
- A remote/plugin marketplace or automatic execution of downloaded code.
- Multiple simultaneous Discord WKWebViews or multi-account architecture.
- Claiming that live calls or Apple Music exact-position access work without
  their manual release gates.
- Developer ID signing or notarization without the required credentials and
  approval; the release may retain the current ad-hoc fallback while making
  the limitation explicit.

## Workstream A — Discord compatibility shield

### Design

Add a small compatibility model and probe coordinator rather than scattering
selector assumptions throughout the runtime.

The page probe returns only bounded, non-content facts:

- supported route kind;
- document generation identifier;
- presence of semantic anchors for navigation, message rows, composer,
  attachments, call HUD, notification surface and activity dispatch;
- supported browser/media capabilities;
- probe version.

Swift stores a bounded `DiscordCompatibilitySnapshot` with feature states:
`healthy`, `degraded`, `unsupported` or `unknown`. Each enhancement checks its
own feature state before installing observers, controls or styles. A failed
probe leaves Discord's native behavior alone and disables only the affected
Noko feature.

Injection is limited to supported application routes. Login, OAuth, settings,
download and unrelated Discord routes receive no Noko page behavior.

Hashed Discord classes remain permitted only as named, documented fallbacks.
Semantic attributes, ARIA roles, stable element relationships and visible
postconditions are preferred.

### Performance and lifecycle rules

- Observe targeted roots after they exist; inspect added subtrees instead of
  rescanning the entire document.
- Never scan editor mutations for media or message rows.
- Coalesce at most one relevant scan per animation frame.
- Give each document a generation token and reject callbacks from older
  generations.
- Cancel all presence, media and page tasks on reload, clear, detach and
  process termination.
- Keep diagnostics bounded to feature state and sanitized failure categories.

### User experience

The Discord workspace remains visible during degradation. A compact notice and
the Tans Inspector identify the affected feature, the last probe result and the
available recovery action without exposing page content or raw JavaScript.

## Workstream B — Tan trust, capability and recovery model

### Trust ledger

Replace enabled-ID-only consent with a per-package trust record containing:

- package ID;
- approved content hash;
- target and declared capabilities;
- trust origin (bundled, imported or translated);
- enabled state;
- health state;
- failure count and last failure time;
- last-known-good hash;
- previous package snapshot reference.

Changing code, target, capabilities or trust origin invalidates consent and
places the package in a disabled/quarantined state until the user explicitly
reviews it again.

Trust records and package replacement use atomic writes with recovery from a
corrupt or interrupted state. The package remains disabled after replacement
until explicit re-enable.

### Capability boundary

Third-party page-world Tans receive no mutating native bridge. App-owned media,
bookmark, notification and workspace controls move to a private/isolated
content-world path wherever possible. Future third-party native actions must be
named capabilities with package identity, payload limits and rate limits.

The initial supported native capability remains `appearance.read`. A scoped
`bookmarks.write` capability is deferred until package identity can be
validated at the content-world boundary and its UX is reviewed.

### Failure isolation and quotas

Preserve the existing disposer ceiling and add central quotas for timers,
observers, mounted elements, bridge calls, package storage and translation
archives. Helper failures are caught, categorized and counted. Repeated
failures persist into quarantine without disabling unrelated Tans or the
Discord workspace.

### Health UI

Tan Hub and Tans Inspector use one shared health presentation:

- Healthy, Disabled, Quarantined or Reload Required;
- target, capabilities, trust origin and approved hash;
- last failure category and time;
- Retry, Disable, Start Safe Mode, Restore Previous Version and Copy Redacted
  Diagnostics actions.

Page-world warnings must state plainly that page-world code runs beside
Discord's own JavaScript and is not a strong sandbox.

## Workstream C — calls and Apple Music

### Call readiness

Add a native diagnostic model backed by a minimal page probe. It reports
WebKit origin, `mediaDevices`, microphone/camera permission state, WebRTC/DAVE
feature availability, Discord call-surface readiness and current capture
state. It never reports a connected call from capture state alone.

Disconnect is scoped to the active call surface and only clears native state
after Discord's leave postcondition is observed and capture returns to `.none`.
Reload/Home navigation during a live call is blocked or explicitly confirmed.

### Apple Music

Fix the event reducer so pause/stop cannot preserve stale presence, and add
helper launch, watchdog, backoff, termination and error diagnostics. Keep the
notification-derived fallback when Automation access is unavailable and label
that limitation honestly. Exact-position support is not considered shipped
until a signed-build manual gate passes.

## Workstream D — new Tans

New Tans are deliberately capability-free and isolated from native mutation.

### `noko.focus-shield`

An opt-in stream/screen-sharing privacy overlay that hides or redacts server
names, DM previews, avatars, activity, notification text and other selected
surfaces. It must expose a clear active indicator, preserve message layout
when possible, and disable cleanly without touching account state.

### `noko.code-workbench`

An opt-in code-block enhancement that adds wrapping, language labels, line
numbers, collapse/expand and reliable copy affordances. It must use delegated
events, avoid editor nodes, respect reduced motion, and never fetch, persist or
execute code.

Read Later, native attachment actions and call tooling remain deferred until
their native capabilities are designed and reviewed.

## Workstream E — build, packaging and release integrity

Use one machine-readable release metadata source for edition, Apple version,
public version, build number, deployment target and bundle identities. Build
scripts, the verifier and Xcode settings consume that source instead of
duplicating literals.

Make Xcode and the shipping CLI path produce equivalent app bundles, including
the NokoMusicWatch helper and reviewed resources. Add deterministic ZIP and
SHA-256 packaging and verify the exact packaged bytes.

C1.3.0 targets Apple version `1.3.0`, public version `C1.3.0` and build `6`.

## Documentation and agent guidance

The release adds or updates:

- `docs/C1.3.0_CHECKLIST.md` — the executable release checklist;
- `docs/DISCORD_COMPATIBILITY.md` — probes, selector policy and compatibility
  diagnostics;
- `docs/TAN_TRUST_MODEL.md` — consent, capabilities, quotas, quarantine and
  rollback;
- `docs/TANS.md` — schema and runtime contract;
- `docs/DEVELOPER_GUIDE.md` — build, test and packaging instructions;
- `README.md` and `RELEASE_NOTES.md` — user-facing release information;
- `AGENTS.md` — Chiaki invariants, workstream boundaries and release push
  behavior.

Two personal Codex skills will be created after this design checkpoint:

- `nokocord-release` for planning, verifying, packaging, committing, tagging
  and pushing Chiaki releases;
- `nokocord-tan` for designing, implementing and reviewing Tans against the
  trust, lifecycle, compatibility and quota contract.

## Verification strategy

### Automated

- Swift unit and WebKit fixture tests;
- trust-ledger storage corruption, hash invalidation, update and rollback
  tests;
- Safe Mode zero-injection tests using a Discord-origin fixture;
- selector-drift and route-gating tests;
- observer performance-budget tests;
- call state and postcondition tests;
- Apple Music reducer/helper lifecycle tests;
- translator and broker suites;
- Xcode Debug/Release and shipping CLI builds;
- signature, entitlement, architecture, privacy and package checks;
- `git diff --check`.

### Manual release gates

- two-user voice call for at least ten minutes;
- microphone/camera denial and recovery;
- Apple Music cold start, pause, stop, seek, repeat and relaunch;
- helper exit after app quit;
- sleep/wake and minimize/reopen;
- Safe Mode and recovery;
- sixty-minute Discord session with typing, reverse scroll, media, composer,
  navigation and compatibility diagnostics;
- fresh ZIP extraction and launch;
- release page assets and hashes match the verified package.

The current Command Line Tools environment lacks XCTest. C1.3.0 cannot claim
the full gate until an Xcode-equipped environment runs it.

## Commit sequence

1. Design, checklist and agent-guidance checkpoint.
2. Compatibility shield and Safe Mode.
3. Tan trust ledger, capabilities and recovery UI.
4. Calls, Apple Music and build parity.
5. New Tans and Tan documentation.
6. Version bump, packaging, final verification and release notes.
7. Annotated `chiaki-C1.3.0` tag, branch push and GitHub Release with assets.

Each commit must leave the tree buildable or explicitly document why a
transitional commit cannot be built. No generated packages, private state,
credentials or agent process notes enter the repository.
