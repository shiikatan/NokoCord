# NokoCord Chiaki C1.3.0 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Execute this plan task-by-task with a red-green-refactor cycle, focused commits, and review checkpoints. Do not skip the release checklist or claim completion without fresh verification.

**Goal:** Ship Chiaki C1.3.0 as a reliability and trust release: Discord-origin-safe compatibility behavior, a real zero-script Safe Mode, hash-bound Tan trust with atomic recovery, bounded page integrations, truthful call/music diagnostics, reproducible release packaging, and two useful capability-free Tans.

**Architecture:** Keep one persistent Discord WKWebView as the only authenticated surface. Add a compatibility boundary between page probes and features, a durable Tan trust ledger between discovery and activation, and explicit lifecycle/capability boundaries around every page-world integration. Keep native call/music adapters diagnostic and fail-open; no credential transport, CEF, broker, second WebView, self-bot behavior, or remote marketplace.

**Tech Stack:** Swift 6, SwiftUI, WebKit, AVFoundation, ScreenCaptureKit, XCTest, Swift Package Manager, Xcode, Node.js translator tests, shell/Python release tooling, and deterministic ZIP/SHA-256 packaging.

**Spec:** docs/superpowers/specs/2026-09-28-c1.3.0-design.md

## Global Constraints

- Work only on the Chiaki branch and preserve the existing Maomao and neutral noko lines.
- Preserve Discord ownership of authentication, messages, media, and recovery material.
- Safe Mode must install zero page scripts, zero message handlers, and zero native bridges.
- A compatibility failure must disable only the affected feature and leave navigation and messaging usable.
- Tan consent is bound to content identity, not merely a Tan identifier; replacement is atomic and recoverable.
- Page-world code cannot invoke mutating native actions in this release.
- Every production change starts with a failing focused test or fixture assertion.
- Keep generated reports, local packages, agent notes, and private recovery material out of source control.
- Use the C1.3.0 checklist as the release authority and mark evidence only after it exists.

- Start with failing tests for approval identity, content hash changes, malformed storage, atomic replacement, rollback, quarantine, and concurrent reads/writes.

- Persist quarantine after repeated startup/runtime failures and provide an explicit recovery operation.

## Execution and review protocol

- Shared-file work is serialized. TanRuntime.swift, BrowserEngine.swift, TanManager.swift, and release metadata must have one active writer at a time.
- Delegate disjoint slices to subagents only after the relevant failing tests and acceptance criteria are explicit. Review every returned diff before keeping it.
- After each focused commit, run the smallest relevant test set; after the final integration, run the complete gate.
- If a task reveals a design conflict, stop that slice, record the concrete evidence in the checklist, and resolve it against the approved design before continuing.
- Do not broaden C1.3.0 into a second transport, credential feature, remote marketplace, native Discord call stack, or unverifiable platform claim.
